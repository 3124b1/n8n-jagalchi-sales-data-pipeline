# 프로젝트 경험: 운영자가 이해할 수 있는 데이터 처리 기준

[프로젝트 소개](../README.md)

## 문제와 나의 역할

기업은 여러 채널의 판매 현황을 한눈에 보고 싶어 했습니다. 이를 위해서는 채널별 상품 이름, 데이터 구조, 거래 상태와 제공 지표의 차이를 먼저 정리해야 했습니다. 프로젝트가 끝난 뒤 전담 개발자가 없는 환경에서도 활용할 수 있어야 했습니다.

저는 4인 팀에서 데이터 자동 취합 파이프라인 설계를 주력으로 맡았습니다. 결과보고서의 업무분담에는 채널별 수집 방식 파악, 상품명·SKU 표준화, n8n·API 취합 흐름, Sheets 저장 구조와 BI 연동이 포함됩니다. 세부 코드 전체의 단독 저작을 입증하는 변경 이력은 공개하지 않았으며, KPI·특이 거래 기준·대시보드 검수·인수인계는 팀 협업입니다.

## 수행 과정

카페24에서는 주문·회원정보와 방문·매출·유입 데이터를 검토했습니다. 바로 제공되는 값과 원천 데이터를 결합해야 얻는 지표를 구분했습니다. 네이버는 당시 인증·파일 제약에 따라 담당자의 다운로드·입력 이후 단계를 자동 처리하는 범위로 정했습니다.

상품명 정제에는 옵션의 제품명, 세트·단품 여부, 콜라보 표기, 어종 등을 반영했습니다. 기업 담당자와 거래 성격을 확인해 테스트 결제와 실제 판매를 구분하려 했습니다. 고객 집계에서는 주문과 회원정보를 결합해 월·성별·연령대 기준을 만들고 구매자 수와 주문 수를 따로 계산했습니다.

주문·고객 집계는 식별키 기준 갱신·추가로 구성했습니다. 단, 첨부 JSON의 방문·유입 흐름은 추가 저장이므로 동일한 방식으로 설명하지 않습니다. 운영자가 사용하는 저장 도구와 대시보드를 연결하고 사용 가이드·인수인계 문서를 마련했습니다. 보고서에는 2026-08-18 대면 인수인계가 기록되어 있습니다.

## 유지보수에 대한 생각

프로젝트 시작부터 ‘내가 이 기업의 직원이라면 이 시스템을 어떻게 받아들일까’를 기준으로 삼았습니다. 도구를 배우는 부담, 처리 기준을 이해할 수 있는지, 문제가 발생했을 때 어디를 확인할 수 있는지가 중요했습니다.

이 경험은 유지보수를 도구 선택과 문서화, 데이터 기준의 명확성까지 포함해 생각하는 계기가 됐습니다. 유지보수를 중요하게 생각했다는 태도와 모든 운영 위험을 해결했다는 주장은 구분합니다.

## 결과와 이후 개선

수집·정제·BI 조회 기반을 마련한 것은 팀의 구현 결과입니다. 이후 기업의 매출 증가, 의사결정 개선 정도, 실제 업무 시간 절감률은 현재 자료로 입증하지 않습니다.

공개 자료 정리 중 원본 JSON의 문법 오류와 일부 저장 방식의 한계를 확인했습니다. 문법 오류는 공개본에서 수정하고, 나머지는 [한계 문서](04-validation-and-limits.md)에 남겼습니다. 이는 프로젝트 수행 당시 성과와 구분한 후속 검토입니다.
